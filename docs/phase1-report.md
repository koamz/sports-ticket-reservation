# گزارش فاز اول پروژه پایگاه داده

## عنوان پروژه
سامانه جامع رزرو و خرید بلیط مسابقات ورزشی

## هدف فاز اول
هدف فاز اول، طراحی ساختار پایگاه داده برای سامانه رزرو و خرید بلیط مسابقات ورزشی بود. در این فاز موجودیت‌های اصلی سیستم، ارتباط بین آن‌ها، کلیدهای اصلی و خارجی، محدودیت‌ها و ساختار کلی جداول طراحی شدند.

## ابزارهای استفاده‌شده
- MySQL
- DataGrip
- Git و GitHub
- ER Diagram

## موجودیت‌های اصلی سیستم
در طراحی پایگاه داده، جدول‌های زیر در نظر گرفته شدند:

- roles
- cities
- users
- sports
- teams
- venues
- matches
- ticket_categories
- tickets
- reservations
- payments
- reports
- football_details
- volleyball_details
- basketball_details

## توضیح جدول‌ها

### جدول users
این جدول اطلاعات کاربران سیستم را نگهداری می‌کند. هر کاربر دارای نام، نام خانوادگی، ایمیل، شماره تلفن، رمز عبور هش‌شده، وضعیت حساب و نقش کاربری است.

### جدول roles
این جدول نقش‌های کاربران را مشخص می‌کند. برای مثال کاربر عادی و پشتیبان سایت.

### جدول cities
این جدول اطلاعات شهرها و استان‌ها را ذخیره می‌کند و برای محل سکونت کاربران و محل برگزاری مسابقات استفاده می‌شود.

### جدول sports
این جدول نوع ورزش‌ها مانند فوتبال، والیبال و بسکتبال را ذخیره می‌کند.

### جدول teams
این جدول اطلاعات تیم‌ها را نگهداری می‌کند و هر تیم به یک نوع ورزش متصل است.

### جدول venues
این جدول محل‌های برگزاری مسابقات مانند ورزشگاه یا سالن را ذخیره می‌کند.

### جدول matches
این جدول اطلاعات مسابقات را ذخیره می‌کند. هر مسابقه شامل نوع ورزش، محل برگزاری، تیم میزبان، تیم مهمان و زمان برگزاری است.

### جدول ticket_categories
این جدول رده یا نوع بلیط‌ها مانند عادی، ویژه و VIP را مشخص می‌کند.

### جدول tickets
این جدول اطلاعات بلیط‌ها را ذخیره می‌کند. هر بلیط به یک مسابقه و یک رده بلیط مربوط است و شامل قیمت، ظرفیت کل و ظرفیت باقی‌مانده است.

### جدول reservations
این جدول رزروهای کاربران را مدیریت می‌کند. هر رزرو به یک کاربر و یک بلیط متصل است و دارای وضعیت، زمان رزرو و زمان انقضا است.

### جدول payments
این جدول اطلاعات پرداخت‌ها را ذخیره می‌کند. هر پرداخت به یک رزرو مربوط است و شامل مبلغ، روش پرداخت، وضعیت پرداخت و زمان پرداخت است.

### جدول reports
این جدول برای ثبت گزارش مشکلات توسط کاربران استفاده می‌شود. کاربران می‌توانند مشکلات مربوط به رزرو یا بلیط را گزارش کنند.

### جدول‌های جزئیات ورزشی
جدول‌های football_details، volleyball_details و basketball_details برای ذخیره ویژگی‌های اختصاصی هر نوع مسابقه طراحی شده‌اند؛ مثل نام لیگ، شماره جایگاه، ردیف، صندلی و امکانات.

## روابط بین جدول‌ها
روابط اصلی پایگاه داده به صورت زیر طراحی شدند:

- هر نقش می‌تواند چند کاربر داشته باشد.
- هر شهر می‌تواند چند کاربر و چند محل برگزاری داشته باشد.
- هر ورزش می‌تواند چند تیم و چند مسابقه داشته باشد.
- هر محل برگزاری می‌تواند چند مسابقه داشته باشد.
- هر مسابقه دارای یک تیم میزبان و یک تیم مهمان است.
- هر مسابقه می‌تواند چند نوع بلیط داشته باشد.
- هر کاربر می‌تواند چند رزرو داشته باشد.
- هر رزرو مربوط به یک بلیط است.
- هر رزرو می‌تواند یک پرداخت داشته باشد.
- هر کاربر می‌تواند چند گزارش ثبت کند.
- هر بلیط می‌تواند جزئیات اختصاصی فوتبال، والیبال یا بسکتبال داشته باشد.

## کلیدها و محدودیت‌ها
در طراحی جداول از موارد زیر استفاده شده است:

- Primary Key برای شناسایی یکتای هر رکورد
- Foreign Key برای حفظ ارتباط بین جداول
- Unique Constraint برای جلوگیری از تکرار ایمیل، شماره تلفن و بعضی مقادیر مهم
- Check Constraint برای جلوگیری از ورود داده نامعتبر، مثل قیمت منفی یا ظرفیت نامعتبر
- Enum برای وضعیت‌هایی مثل وضعیت رزرو، پرداخت و حساب کاربری

## نرمال‌سازی
ساختار پایگاه داده به گونه‌ای طراحی شده که از تکرار غیرضروری داده‌ها جلوگیری شود. اطلاعاتی مانند شهرها، نقش‌ها، ورزش‌ها، تیم‌ها، محل‌های برگزاری و رده‌های بلیط در جدول‌های جداگانه ذخیره شده‌اند. این طراحی باعث می‌شود پایگاه داده خواناتر، قابل توسعه‌تر و سازگارتر باشد.
